当前切分规则：

- 不跨越 ASR segment。
- 一级标点 `。！？!?；;，,` 直接作为切分边界。
- 顿号 `、`、冒号 `：:` 平时不主动切分。
- 一级切出的片段超过 32 个可见字符时，向前寻找最近的顿号或冒号切分。
- 最终只在片段少于 3 个可见字符时尝试向前合并。

## 观察结果

### 1. 语气词会被保留，并且可能黏在前后句

例如：

```text
一般来说呢，呃，
相对来说云端的模型更加呃准确一点，
有了云端的模型其实我们就不再需要用 AI 校对了。好，
```

当前规则只看标点和长度，不理解“呃”“好”在语义上是插入语还是下一句开头，所以不会主动清理或重新归属。

### 2. 当前结果数量明显偏多

176 条字幕对于 6 分钟多的口播偏碎，主要原因不是 32 字上限，而是一级规则把几乎所有逗号都直接切开了。例如：

```text
这个音频呢放到我们的视频，
这个视频的呃资源库里，
然后素材库里，
点击保存，
```

这些句子虽然满足“按逗号切分”，但字幕观感会比较碎。

### 3. ASR 本身有识别问题，切分规则不能解决

例如：

```text
Sub4j / Sub4Sub / Sub4
这个妻子修改了
这个的字字幕
```

这些属于 ASR 识别或专有名词问题，应由人工校对或后续校对功能处理，不应让切分器负责。

### 4. 发现一个短句边界问题

第一条结果是：

```text
好，
```

它只有 2 个可见字符，但因为它是第一条，没有前一个字幕可以合并。说明“少于 3 字向前合并”还需要补充“如果是首条，则向后合并”的规则。

### 5. 本次没有跨越 ASR segment

所有切分都限制在各自的 ASR segment 内，当前实现满足这个硬约束。
